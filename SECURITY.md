# Security

What protects the tool, and what does not. For interviewers, and for anyone reviewing the tool.

## What it is

This is not a hosted service. There is no server, no cloud deployment and nothing listening on a network. It is a local tool. The interviewer runs it on their own machine and shares one link with the candidate, who works in the browser (editor, terminal, AI chat). The AI assistant is one of three, chosen by the candidate from what the interviewer allowed: the chat (the Claude Code CLI, started on the interviewer's machine for each message), or Claude Code, OpenCode or Pi running in a terminal in the page. All of them run on the interviewer's machine with the interviewer's own login, so the interviewer's account pays for them. Candidate work stays in `.solutions/` (gitignored) on that machine. The tool sends no telemetry.

## What is in place

- **Network.** Frontend and backend are bound to loopback, so the tunnel is the only way in. CORS allows the app's own origin only.
- **Interview link.** The tunnel address is not a secret and may repeat (a free ngrok account always gets the same one). What protects the interview is a private part in the link, made by `make start` for every interview, kept only in the environment of the running servers and never written to disk. It rides after a `#`, so it is not sent to any server or written in a log. The page trades it once for an HttpOnly cookie, and the servers answer a candidate (API, WebSockets, preview) only with that cookie. An address on its own, a link from an earlier interview, or a guess gets a 401. The interviewer on `localhost` is not asked for it. Running the servers without `make start` (plain `npm run dev`) turns this off.
- **Roles.** `localhost` is the interviewer, the tunnel is a candidate. Interviewer endpoints (candidate list, preview ports, workspace reset, hidden files) answer 403 to candidates, and a forged forwarding header does not change that (the role reads the last entry, the one the nearest proxy wrote; checked with a forged header through Next.js and with ngrok). A candidate screen can start its own workspace but cannot switch the interview to a folder that already belongs to someone else. Requests to the interviewer side must come from the app itself: another site's Origin, a cross-site fetch or a cross-site WebSocket is refused.
- **Candidate code in the interviewer's browser.** The interviewer's preview frame loads the candidate's app from port 3099, a second port of the same server that only serves `/preview/`. A different port is a different origin, so a page the candidate wrote cannot read the interviewer's API or page, and the interviewer's powers are not granted on that port. It is the same site, so the app's own cookies (a login) still work. Port 3099 listens on this machine only.
- **Files.** Paths resolve inside the candidate's own folder, symlinks included, for reads and writes, and the file routes refuse to work without an active candidate. Locked files are read only on the server, however the path is written (`./`, `../`, case). Hidden files are not in the candidate's folder at all and cannot be recreated by the candidate.
- **Names.** Candidate names and exercise ids are plain names only (letters, digits, `_`, `-`, `.`), since they become folders.
- **Exercise apps.** The exercise dev server and API listen on `127.0.0.1` only; the platform proxies them.
- **Terminal.** Only allowlisted programs start, paths outside the exercise are refused, and the shell gets a reduced environment without tokens.
- **AI assistant.** No MCP servers, browser or skills. The system prompt keeps it to the exercise: it steers away from questions about the machine, accounts, tokens, the interviewer or its own instructions, without discussing its rules, and it starts with an overview of the project so it needs no exploration. Spending is whatever the interviewer's account allows, so use an account with a limit.
- **Who chooses the assistant.** The candidate picks in the interview, and the interviewer can pick too, to rehearse alone or to set the room up. Whoever picks last decides, and both see the same screen. The server refuses an unknown tool and a tool the interviewer did not allow in `interview.config.yaml`, to either of them and however the request is made; hiding a button is not what enforces it. The chat is always allowed, so a candidate is never left without an assistant. The reason a tool cannot start (login, budget, install) is shown to the interviewer only.
- **Terminal assistants (Claude Code, OpenCode and Pi).** Each runs in a real terminal on the server, one per candidate and exercise, and every screen attached to it sees the same terminal. Each gets a private configuration folder next to the candidate's work, so nothing of the interviewer's own setup comes along: no status line, hooks, plugins, skills, MCP servers or commands. Only the login is copied in (the provider the interviewer already uses), and only from the interviewer's own configuration or environment. The folders are created with the login file readable by the owner only. Claude Code starts with `--strict-mcp-config`, `--no-chrome` and the same blocked tools as the chat; OpenCode starts with `--standalone` (so it does not attach to the interviewer's background service), ignores a project configuration file written by the candidate (checked: without this, a candidate's `opencode.json` changes the model and can add tools) and has web fetch, web search, image generation and sub agents removed. Pi keeps its configuration and sessions in the same kind of private folder, starts with no extensions, skills, prompt templates, themes or context files, starts offline (no update check, no install ping), takes its login from what the interviewer already has for Pi (a saved `/login` sign in or key in `~/.pi/agent`, or a provider key Pi documents, such as `ANTHROPIC_API_KEY`) and copies only that one provider into its private folder. When there is no Pi login it can use the model router the interviewer's Claude Code uses (`pi:` in `interview.config.yaml`): the router's key never reaches Pi's process, its environment, its folder or its logs. Pi gets the address of a forwarder the server runs on the loopback address for that one session, with a random key that works only there, and the forwarder passes on only the paths a model call needs and closes when Pi ends. This is the reason: a candidate's shell inherits what Pi has, so a key given to Pi would be a key given to the candidate. It never reads the router, cloud or gateway variables of other tools (`ANTHROPIC_AUTH_TOKEN`, `AWS_*`), removes every key variable from what it runs with, and refuses a key that is a shell command.
- **Settings file.** `interview.config.yaml` is local and gitignored. A missing or broken file allows everything, so it never stops an interview. It decides which assistants are offered and which exercises `make start` lists. Candidates are never sent the file.
- **Code quality.** Type check, lint and tests run on every pull request, including tests that try to break the role and tool rules.

## Limits

1. **The candidate's code runs as the interviewer's user.** The terminal checks the first word of a command, not what the program does. It is a guard rail, not a sandbox.
2. **The chat is kept on the exercise by instructions, the terminal assistants by the operating system.** The chat (Agent mode) can be talked into reading outside the folder by a determined candidate. Claude Code, OpenCode and Pi run with permission prompts off, so they would read anything the interviewer's user can, and in testing Claude Code read a file two folders above its own and listed what comes before it. They now run inside the operating system's sandbox, which stops every program they start (cat, python, node, their own file tools), not just their own tools: they read and write their own folder and nothing else, not the interviewer's home or keys, not the settings of the interview, not another candidate, not the phases that are still hidden, and not the temporary folders where the interviewer's other sessions of the same tools keep their files. This was checked with the real programs against attempts to read each of those, and a test runs ordinary programs inside the generated profile. What it does not do: it does not close the network (the code and the assistant can still send things out), it works on macOS only so far (elsewhere these assistants do not start, instead of starting unprotected). Claude Code used to be the exception: its own sandbox covers the commands the model runs but not what a person types after `!` in its terminal (measured: that read a file in the interviewer's home, `interview.config.yaml`, another candidate's folder and a hidden phase). It is now wrapped as a whole process like the other two, with its own sandbox switched off because a sandbox cannot be started inside another one (the system refuses it). Its permission switches that keep its file tools in the folder stay on. The same attempts, typed after `!` or `!!` in each of the three terminals, are all refused, and a control run without the wrapping read every one of them. What was not seen: the model's own Bash tool running under the wrapper with a real model. Any command it starts is a child of the wrapped process and carries the same limits (shown with a shell, python and node started from one another). Two costs show: every shell command of Claude Code reports exit code 1 and an 'operation not permitted' line for a control file it writes in /tmp, though the output is complete and the assistant says so, and a program that needs a setuid tool such as `ps` cannot run. A provider can also add a web search tool of its own that a client side setting does not remove; in testing both refused to search the web when the interview rules were loaded, which is the instruction doing its job, not a block.
3. **No egress filtering.** The candidate's code can reach the internet.
4. **The link is the only secret.** There is no login. Whoever has the full link during the interview can open the candidate's workspace, so send it only to the candidate. It stops working at the next `make start`.
5. **Role relies on the tunnel's forwarding headers.** Checked with ngrok, and with a cloudflared quick tunnel: through it, a request without the cookie got 401, one with it was treated as a candidate (403 on the interviewer's routes), and a forged `Host` or `x-forwarded-host` of `localhost:3000` was still refused. The terminal assistants and the presence socket (WebSocket) came through cloudflared with about 0.2 seconds of delay. The chat's live stream (server sent events) did not: in 75 seconds through a cloudflared quick tunnel none of its events arrived, while on `localhost` the first came at once and a ping every 10 seconds, so Agent mode cannot answer through it. A named cloudflared tunnel, which needs an account and a domain, was not tested. Other tunnels have not been tried, and a link just made can take a while to open on some networks, because the name has not reached the resolver yet.
6. **The terminal assistants run with permission prompts off.** They edit and run things without asking, the same as the chat, because a prompt nobody is watching would stop the candidate. The folder and the supervision are what limit them.
7. **The OpenCode and Pi logins are copied into a folder on this machine.** The private folder under `.solutions/` holds a copy of the provider login (for Pi, in its `agent/auth.json`), and it is not encrypted (the file is readable by its owner only). Delete a candidate with `make delete` when the interview is done.

## How we run it

Interviews are supervised and the candidate shares their screen. Use a machine and account without production credentials. A dedicated account, VM or container is the stronger setup if the limits above are not acceptable.

## Protocols this covers

A short list of what the tool is checked against, so a reviewer can find the part that answers each question.

| Question | Where it is answered |
| --- | --- |
| Who can reach it? | Network, Interview link, Roles |
| Who can change what the AI does? | Who chooses the assistant, Settings file |
| What can the AI and the candidate's code touch? | Files, Terminal, Terminal assistants, Limits 1 to 3 |
| What leaves the machine? | Nothing except the calls the assistants make to their provider and the tunnel. No telemetry. Limit 3 covers what candidate code can send. |
| What is stored and for how long? | Candidate work in `.solutions/` (gitignored), the provider login copy (Limit 7) |
| How is it checked? | Type check, lint, tests that try to break the role and tool rules, a code scan and a secret scan are not part of this repository, so run your own before you publish a change. |

### Reporting a problem

Open a private security advisory on the repository, or contact the maintainer, with the steps and what you saw, not a working exploit. Do not post an interview link or a login key anywhere public: a link only stops working at the next `make start`.
